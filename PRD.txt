1. EXECUTIVE SUMMARY
--------------------------------------------------------------------------------

NaturaAI is an AI-powered healthcare and herbal intelligence platform that enables
users to discover safe, effective natural remedies using medicinal plants, herbs,
flowers, roots, fruits, and other naturally occurring ingredients. The platform
combines a curated herbal knowledge base, an ensemble machine-learning (ML)
prediction engine, a personalized recommendation engine, a grounded large
language model (LLM) health assistant, and a plant-recognition capability.

The core differentiator is *safety-first, evidence-aware personalization*: every
prediction is contextualized against the user's age, gender, existing conditions,
allergies, and medications, and every output carries a verdict
(SAFE / CAUTION / UNSAFE), quantitative safety/benefit/risk/confidence scores,
preparation guidance, dosage, and usage frequency.

The platform is architected as a three-tier monorepo (Next.js frontend, Spring
Boot REST backend, Python/FastAPI ML engine) with PostgreSQL, Redis, RabbitMQ,
and Qdrant backing storage, caching, async messaging, and vector search. It is
already deployed on free-tier infrastructure (Vercel, Render, Neon) and runs a
full three-suite CI pipeline. NaturaAI is currently an educational product and is
positioned for evolution into a commercially viable consumer-health platform.

3. PROBLEM STATEMENT
--------------------------------------------------------------------------------

3.1 Market / User Problem
-------------------------
- Traditional herbal knowledge is vast but fragmented, often undocumented, and
  inconsistently applied.
- Consumers frequently combine multiple herbs without reliable information about
  safety, interactions, appropriate dosage, or contraindications for their
  specific health profile.
- Existing online sources are generic (one-size-fits-all), not personalized, and
  rarely contextualized to age, gender, co-morbidities, allergies, or
  medications.
- There is a high risk of adverse interactions (e.g., honey and diabetes,
  licorice and hypertension, ashwagandha and thyroid medication) that generic
  advice fails to surface.
- Individuals, students, and wellness practitioners lack a single, credible,
  interactive tool to reason about herbal combinations and obtain preparation
  and dosage guidance.

3.2 Why Now
-----------
- Growing global interest in natural and traditional medicine and preventive
  wellness.
- Advances in ML, LLMs, and embedding/vector search make personalized,
  evidence-grounded reasoning practical at consumer scale.
- Low-cost cloud and free-tier infrastructure (Vercel, Render, Neon) allow a
  full-stack, production-grade deployment at near-zero operating cost.

7. PRINCIPLES & DESIGN TENETS
--------------------------------------------------------------------------------

1.  Safety over optimization - never optimize for engagement at the cost of
    safety or accuracy.
2.  Grounded AI - prefer knowledge-base grounding over unconstrained generation;
    the LLM is an explainer, not the source of truth.
3.  Personalization with caution - personalize aggressively but always surface
    condition/allergy/medication-specific warnings.
4.  Honest confidence - every score is disclosed; unknown pairs default to
    CAUTION, never to unverified SAFE.
5.  Graceful degradation - the core app works even when the ML engine is
    unreachable (rule-based fallback).
6.  Evidence traceability - curated records carry a scientific-confidence
    score; datasets are attributed (e.g., Amidha dataset, CC-BY-4.0).
7.  Transparency of disclaimer - every consumer-facing output carries a
    medical-disclaimer notice.

9. NON-FUNCTIONAL REQUIREMENTS
--------------------------------------------------------------------------------

NFR-1 Performance
    - Analysis response p95 < 3.0 s (target < 1.5 s) including ML round-trip.
    - Frontend first-contentful paint < 2.5 s on 3G; static pages pre-rendered.
    - ML prediction p95 < 800 ms for a 2-5 ingredient set.

NFR-2 Scalability & Availability
    - Stateless backend (JWT) horizontally scalable; Redis for cache.
    - Graceful degradation when ML engine is down (rule-based fallback).
    - Uptime target >= 99.5% on deployment hosts.

NFR-3 Security
    - JWT signed with a 32+ byte secret; Authorization header enforcement via
      JwtAuthFilter on protected endpoints.
    - Passwords hashed with BCrypt; secrets only in host dashboards (never
      committed); .env git-ignored; .env.example placeholders only.
    - Scoped CORS via ALLOWED_ORIGINS (never "*" in production).
    - ML OPENAI_API_KEY server-side only; never exposed to the frontend.
    - Security policy published (SECURITY.md) with private disclosure path.

NFR-4 Compliance, Safety & Ethics
    - Every consumer output carries the medical disclaimer.
    - No definitive medical claims; assistant ends with a safety disclaimer.
    - Data handling documented (profile PII: age, gender, country, conditions).

NFR-5 Reliability & Quality
    - Three automated test suites must pass on every main merge (CI gate).
    - Model artifact smoke-tested at training time; corrupt artifact falls back
      deterministically (no silent degraded behavior).
    - Deterministic, seeded scoring to keep outputs stable and auditable.

NFR-6 Maintainability
    - Monorepo with per-tier README, docs/architecture.md,
      docs/database-schema.sql.
    - Adhere to repository conventions; automated formatting/lint.

NFR-7 Compatibility
    - Modern evergreen browsers (Chrome, Edge, Firefox, Safari latest-2).
    - Server-rendered/static frontend deployable on Vercel without runtime

10. SYSTEM ARCHITECTURE (SUMMARY)
--------------------------------------------------------------------------------

Browser
   │ HTTP/HTTPS
   ▼
┌────────────────────┐      ┌────────────────────────┐
│ Frontend           │      │ Backend                │
│ Next.js + React 19 │─────▶│ Spring Boot 4 / Java 21│────▶ PostgreSQL (Neon)
│ TypeScript         │ HTTP │ JWT + OAuth2           │───▶ Redis (cache)
│ Tailwind/ShadCN    │      │ JPA / Hibernate        │───▶ RabbitMQ (async)
└────────────────────┘      └───────────┬────────────┘
                                        │ REST
                               ┌────────▼───────────┐
                               │ ML Engine          │───▶ Qdrant (vectors)
                               │ FastAPI (Python)   │───▶ models/predictor.joblib
                               └────────┬───────────┘
                                        │ optional
                                        ▼
                          LLM (Llama 4 / Gemma / Mistral / OpenAI)

Key flows:
1. Analyze: /analyze -> POST /api/v1/remedies/analyze -> ML /predict -> response
   (fallback to rule-based heuristic if ML unreachable).
2. Recommend: /recommend -> disease/avoidance mapping + ML scoring.
3. Suggest: /suggest -> ML-ranked complementary ingredients.
4. Assistant: /assistant -> knowledge base grounding -> optional LLM explainer.
5. Scan: /recognize -> image decode -> recognizer (heuristic stub v1).

Data volumes (v1):
- Herbs: 368+ in backend catalog + 368 in ML plants.csv (Amidha dataset,
  CC-BY-4.0, attributed in footer).
- Combinations: 39 curated pairs with verdicts and scores.
- Diseases: 15 disease-to-herb mappings (symptoms, recommended, avoid).

11. USER JOURNEY (PRIMARY FLOW)
--------------------------------------------------------------------------------

1. Land on homepage (/) - hero, capabilities, featured herbs, stats,
   testimonials.
2. Register / sign in (email or Google); verify email if applicable.
3. Complete or confirm health profile (conditions, allergies).
4. Navigate to "Analyze" -> 4-step wizard:
   a. Health information (conditions, allergies)
   b. Remedy type (internal/external)
   c. Ingredients (chips + search + custom; optional AI suggestions)
   d. Result: verdict badge, five scores, toxicity, benefits, risks,
      preparation, dosage, frequency, rationale, disclaimer.
5. Save/return to dashboard; ask the assistant follow-up questions; scan a
   plant image.
6. Repeat and refine over time; history preserved for the user.

Edge cases:
- Zero/one ingredient -> blocked with clear messaging.
- Unknown ingredient -> added as custom; pairs default to CAUTION with a
  "limited data" warning.
- ML engine down -> heuristic response with identical contract (graceful).
- Diabetic user selecting honey -> surfaced risk note + reduced safety score.

13. AI / ML REQUIREMENTS
--------------------------------------------------------------------------------

13.1 Compatibility Predictor
----------------------------
- Input: ingredient set + remedy type (+ optional profile for personalization
  layer).
- Pipeline: curated pair lookup -> trained model prediction (only for core
  herbs seen in training) -> rule-based hazard/contraindication layer ->
  deterministic seeded scoring.
- Verdict rule: worst verdict across all pairs wins (UNSAFE > CAUTION > SAFE).
- Confidence: curated scientific confidence or model probability; unknown pairs
  default to 55% with a caution note.

13.2 Personalization Rules (examples)
-------------------------------------
- Diabetes: flag honey/sweetening herbs; fenugreek sugar-lowering caution.
- Hypertension: flag licorice/high-sodium preparations.
- PCOS/Thyroid: flag hormone-active herbs (fenugreek, ashwagandha).
- Pollen allergy: cross-reactivity note (chamomile, tulsi).
- Nut allergy: check carrier oils in external formulations.

13.3 LLM Assistant
------------------
- Retrieval-first; provider keys optional (OPENAI_API_KEY / HUGGINGFACE_API_KEY
  / OPENAI_BASE_URL for local Llama 4, Gemma, Mistral via Ollama/vLLM).
- System prompt enforces caution; max_tokens bounded (300); disclaimer appended.

13.4 Plant Recognition
----------------------
- v1 heuristic stub honoring the API contract; v2 trained vision model.

13.5 Model Governance
---------------------
- Training: python -m train.train_predictor (RF, GB, XGB, LGBM; best saved).
- Artifact validation at save time (reload + smoke test).
- Runtime fallback: any failure -> rule-based path, never a crash.
